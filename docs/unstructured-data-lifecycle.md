# 비정형 문서 데이터 수명주기 전략

목표는 오래됐다는 이유만으로 지식을 삭제하지 않으면서 검색 품질, 보관 비용, 개인정보
위험을 함께 관리하는 것이다. 원본, 추출 텍스트, 임베딩을 같은 수명으로 취급하지 않는다.

## 계층

| 계층 | 기본 조건 | 저장 위치 | 검색 처리 |
|---|---|---|---|
| Hot | 최근 30일 조회 또는 인기 점수 상위 | OpenSQL + Redis + MinIO | 즉시 하이브리드 검색 |
| Warm | 31~180일, 최근 조회 없음 | OpenSQL + MinIO | Redis 제외, 즉시 검색 |
| Cold | 181~365일, 법적 보존 대상 또는 낮은 사용량 | MinIO archive prefix/저비용 S3 class | 메타데이터만 검색, 요청 시 복원 |
| Delete candidate | 365일 초과, 보존 의무·Legal Hold 없음 | 삭제 승인 대기 | 검색 제외 후 30일 유예 |

기간은 환경별 정책으로 바꾸며 문서 `updated_at` 하나만으로 결정하지 않는다. 마지막 조회일,
조회 횟수, 문서 소유자, 분류 등급, 법적 보존 여부를 함께 사용한다.

## 처리 원칙

1. 원본은 MinIO/S3에서 버저닝과 암호화를 적용하고 OpenSQL에는 메타데이터와 추적 정보를 둔다.
2. Cold 전환 시 임베딩은 제거할 수 있지만 체크섬과 추출 텍스트 요약은 유지해 재수집을 가능하게 한다.
3. 모델 변경으로 낡은 임베딩은 원본보다 먼저 폐기하고 필요할 때 새 모델로 재생성한다.
4. 개인정보·기밀 등급별 보존 기간을 별도로 적용하고 Legal Hold가 있으면 자동 삭제하지 않는다.
5. 삭제는 `candidate → owner 승인 → 검색 제외 → 30일 유예 → 원본/청크/임베딩 삭제` 순서로 처리한다.
6. 모든 archive/restore/delete 작업을 감사 로그와 Outbox에 기록한다.
7. Redis는 원본 저장소가 아니며 TTL 만료 또는 장애 시 OpenSQL/MinIO에서 재구성한다.

## 운영 주기

- 매일: Redis 인기 점수 감쇠, 만료 캐시 정리, 실패 Outbox 재처리
- 매주: Warm/Cold 후보 보고서 생성 및 소유자 알림
- 매월: 승인된 Cold 이동과 삭제 후보 격리
- 분기: 보존 정책, 개인정보 분류, 복원 훈련과 백업 무결성 검사

자동 영구 삭제는 기본적으로 비활성화한다. 대회 시연에서는 후보 보고서와 Cold 복원까지만
자동화하고, 삭제는 관리자 이중 확인을 요구하는 것이 안전하다.
